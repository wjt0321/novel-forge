# 50 · Lean 迭代计划：砍掉繁文缛节，让一章快速、准确、高效地完成

> 依据：2026-08-30 在一本新书上完整跑通一章的实测记录（26 次角色调用、8128 秒、7 次集中修订调用、8 轮双审、5 次作者授权续修）。
> 目标只有一个作者价值：**用尽量少的角色调用，把一章推到 ready，并且正文真的好看。**
> 本文是计划与缺陷账，不是使用手册；日常创作规则仍以 `docs/43-*`、`docs/44-*` 与 Skill 为准。

---

## 一、实测成本账（问题在哪）

| 阶段 | 角色调用 | 墙钟 | 占比 |
| --- | --- | --- | --- |
| Writer 初稿 | 1 | 351s | 4% |
| 首轮双审 | 2 | 367s | 5% |
| 集中修订 | 7 | 4073s | **50%** |
| 复审 | 16 | 3338s | **41%** |
| 合计 | 26 | 8128s | 100% |

写正文只占 9% 的时间，**91% 花在"改—重审"的循环上**。字数轨迹 5895 → 7483 → 8513 → 9123 → 8848 → 8897 → 8797：稿子越改越长，越长错得越多。

双审共 8 轮，集中修订共 7 次调用（其中 1 次因宿主轮次上限被拒为运输失败，暂存正文保留未重写），作者授权续修 5 次。MUST 曲线（只计被控制面接受的结论）：编辑 4→5→2→3→1→2→1→0，盲审 0→2→0→3→1→1→0→0。**第 2 轮到第 7 轮反复指向同一段**（章末照旧图默画房间的方位标注，共 5 次），而决定卡上只显示"第 N 轮集中修订后仍有 MUST"，作者看不出这是复发。

## 二、根因诊断（五条，按影响排序）

### R1 Lead 越权做文学导演 —— 最大的缺陷来源

Skill 写明"Lead 只分发、等待和调用命令"，实际是 Lead（我）在每轮简报里临场发明写作指令，而这些指令本身有缺陷：

- 指示"证据链保持不均匀、允许他数不准" → 与"一次目视即可复现全屋"的人物支点直接冲突，制造了一条吃掉三轮的 structural。
- 指示"让九〇三的门与拖鞋承担后果" → 产出"他亲手拔走锁舌并记账"加"结尾追问谁拔的"自相矛盾，两位审稿人各自独立命中。
- 指示"麻绳改三人可执行" → 产出"五米对折两股从九楼放到车尾"的物理不可能。

**流程设计是：审稿人声明 MUST，执行归 Writer 与 capsule。Lead 给具体改法，等于在 capsule 之外新增一份永不被审计的判准。**

### R2 正反例存在但一个都没送到角色手里

- 资产是真的：`app/novel_forge/style_corpus.py`（正例基因 + AI 味反例），init 时落到 `books/<slug>/memory/style-reference.md`。
- 三处断线：`workflow_iteration.py` 的 P2 选择器不含基因库；`planning_spec.py` 注释明示示例刻意不进模型上下文；唯一有资格进包的三个槽位（P2「作者认可范例」、voice-bible `exemplar_notes`、「本书采纳的风格基因」勾选表、`voice-seed.md`）**全部是未填的模板占位**。
- 后果：Writer 拿到的**全是禁令，没有一个正面靶子**。八轮双审里 `human_likeness` 一直判 `convincing`，10 条 MUST 抽样里 `blocking=0`，全部是连续性/逻辑问题。**没有一道门问"好不好看"**，所以修订六轮，正文水平移动为零。这正是"写得并不怎么样"的直接解释。

### R3 防循环护栏在真实宿主上等于不存在

`native_relay.py` 的熔断读 `evaluate_budget_breaker(int(state.get("known_total_tokens") or 0), ...)`。宿主不回报 token（`cost-summary` 26 次全部"token 未知"，状态里 `known_total_tokens` 直接缺位），传入恒为 0，`hard` 永不触发。唯一的轮次上限 `MAX_LEAN_SURFACE_PATCH_ROUNDS = 3` 只管表面 Patch，管不到 `authorize-revision`；**`authorize-revision` 没有累计上限**。于是"禁止无限循环"完全依赖作者手动点停止。

### R4 连续性事实没有账本

空间坐标（布告栏/窗帘/烧洞/门/图）、趟次↔载货、件↔批计酬、单据联次↔持有人——四类事实在本章反复破，而 `chapter-editor-input/canon.md` 这章是空的。每轮都由一位新编辑从零重读 8800 字人肉对四本账，且只能报"当前可见的那一条"，改完又破旁边。docs/46 的弧线账本/对白账本存在于代码里，ch01 一个都没用上。

### R5 修订经济学是反的

Skill 的硬门精神被 Lead 转译成"不得因删减而篇幅塌陷"，Writer 便靠补细节填回字数，错误面同步扩张。**唯一真正收敛的一轮是纯删除轮**（下令"删掉该段全部方位句，不再分配墙向"）。当前流程对"改一处的成本"没有任何度量，对"字数增长"没有任何惩罚。

## 四、迭代计划

优先级：P0 = 直接砍掉本章 91% 浪费的；P1 = 影响成品质量的；P2 = 卫生问题。

### P0-1 复审改为"增量重审"，不做全章重读（**未实施，被 P0-2 阻塞**）

现状：每次修订后 Blind 与 Editor 各自完整重读全章（16 次复审、3338s，其中约 85% 的文本上一轮已被判过合格）。

改为：修订轮之后，增量复审只读**被触碰的段落 + 其前后各一段 + 全章机器硬检**；晋升前仍做一次全章双审。判据由 Python 提供：Patch/修订的锚点位置来自 MUST 的 `location`/`evidence`。

实测否证了它的独立可行性：本章编辑抓出的 13 条 MUST 里有 4 条在**未被改动**的段落（沙发规格与门框通过性、四角受力与三人队形、单据签名联流转、封底空白与描图）。只读改动处会把这类跨段矛盾直接放进晋升门。因此本项**必须有 P0-2 的跨段不变量清单作前提**才做，否则是用准确换速度。

本轮改为交付两条零正确性代价的降量：**(a)** 自动续修预算把无打断情形下的双审上限固定为 4 次（原先 1 次修订后必停，之后每轮都要作者授权，实测涨到 8 次双审 16 次复审）；**(b)** 见 P0-3。

### P0-2 start 时强制生成"本章物理账"

现状：canon 为空，连续性事实全靠审稿人脑补。

改为：`planning/scene-package-chNN.md` 新增必填小节**「本章物理账」**，四类表：`空间坐标`、`趟次/次序 ↔ 载货`、`件 ↔ 批 ↔ 金额`、`物件 ↔ 持有人 ↔ 所在位置`。Writer 按表写，Editor 对照表核（不再每轮重读全文找账），Python 用现有 lint/gates 做一致性机检；表中任一行被正文违反即 MUST。

预期：R4 与 R5 的主要成因同时消解——本章那 5 轮方位问题在第一轮就会被表拦下。
成本：作者/Lead 每章多填一张表；表本身就是 Scene Package 的一部分，不新增阶段。

### P0-3 续修走最便宜的路径（已实施）＋ 复发换策略（待定）

**已实施**：所有续修路径（首轮、自动预算轮、作者授权轮）统一走 `_request_next_revision`：全部开放 MUST 都是 `local` 且可唯一定位时用 Python 精确替换，否则才整章重写。实测每次整章重写 582 秒，是最大成本项；原先只有首轮享有局部优先，自动轮与授权轮一律整章重写。

**待定**：同一锚点第 2 次出现时，决定卡不再提供"原样再修一轮"，只提供三项：
1. 删除该处正在承担的表述（默认建议，附锚点）；
2. 接受当前稿（记为未通过，不晋升）；
3. 显式换策略（必须说明与上一轮不同在哪，写入 `authorize-revision --reference`）。

### P0-4 token 未知时的熔断代理

`known_total_tokens` 缺失或为 0 时，改用代理指标：`patch_round >= 2` 为 soft（关闭可选深检），`patch_round >= 3` 为 hard（停在作者决定并说明依据）。同时把 `cost-summary` 在墙钟之外增加"全章重读字符数"这一确定性指标——它不依赖宿主遥测，能真实反映浪费。

### P1-1 修订简报的字数单调约束

集中修订轮默认要求"修订后 CJK ≤ 修订前"；确需增长时必须在 `--reference` 里给出理由。R5 的机制化。

### P1-2 会话真实性

- `complete-role` 对 `--session-id` 目前只做非空检查，一个编造值就能进状态与证据。改为：宿主遥测可得时比对；不可得时要求 `--session-attested`（显式声明该 ID 取自宿主回执），并把缺声明记为运输缺陷而非重做正文。
- 宿主若不在工具结果里回传子代理 ID，Skill 需要给出可执行的取证路径；本次实测只能靠解析宿主自身 transcript。

### P1-3 字段名单源化

Skill 的 Blind Reader / Chapter Editor 段仍在列举结果字段名，与 `planning_spec.LITERARY_MICRO_RULES` + capsule `instructions.md` 三处并存且不一致。实测代价：两次整轮重跑。改为 Skill **只指向 capsule instructions.md，不列字段名**。

### P1-4 `init` 阶段把声音锚变成必答项

`voice-seed.md` 停在 `TODO`、`exemplar_notes` 与基因勾选全空，是 R2 的后半因。`start` 时若三者皆空，输出一次明确提示（不阻断），说明"第一章将使用 style-corpus 默认参照；要换请填 voice-seed 或勾选基因"。

### P2-1 单源一致性

`docs/46`、`docs/49` 已不在 `docs/` 树中，但 `docs/README.md` 指明它们归档在 `archive/history.md`，代码注释（`book_arcs.py:1`、`chapter_sequence.py:135`、`native_relay.py:106` 等 10+ 处）仍可解析，无需改动。`AGENTS.md` 曾把 Writer P0/P1/P2 预算的单源写成 `planning_spec.py`（实际在 `workflow_iteration.WRITER_CONTEXT_BUDGETS`），本轮已改正并顺带标明词库单源 `style_corpus.py`。待定项只剩一个：是否把两处上限定义合并成单一预算模块，避免以后再分叉。

### P2-2 模板与规则不得复制

`project_templates.py` 的 voice-bible 勾选表是本次发现的第二处硬编码副本（已由 D3 消除）。建议加一条测试：模板中任何"列举风格条目"的段落必须来自 `style_corpus` 或 `planning_spec`，禁止字面量列表。

## 五、缺陷与教训账（本文以外不另立文档）

### 控制面缺陷

1. `complete-role` 接受任意非空 `--session-id`（本次一个编造 ID 被写入 `planning/chapter-sequences/auto-ch01-9d83cd0d36.json`；`evidence/` 干净，晋升记录用的是真实终态会话）。**未修正，见 P1-2。**
2. 预算熔断在 token 不可得时永久静默失效。**未修正，见 P0-4。**
3. `authorize-revision` 无累计上限，且决定卡不显示复发。**复发已修（D4），上限未修。**
4. Skill / capsule 字段名不同源，实测造成 2 次无效重跑。**规则已补（D5），Skill 里的字段名清单待删（P1-3）。**
5. `_bounded` 会在 CJK 索引处硬切，把注入到 P2 尾部的条目腰斩（实测出现"对白朴"）。已通过"先算保留额度再收缩前段"绕开；其他使用点仍有同样风险。
6. `render_positive_genes_brief` 默认 1500 字截断，扩库后会静默丢条目；`style-reference.md` 文件头版本字符串写死。已由 D3 修正。
7. `chapter_risk` 默认为 `standard`，第 1 章即卷首也不触发 `approve-high-risk`。若认为卷首应当走高风险门，需要 Python 在 ch01 自动置为 `volume_start`，而不是靠 Lead 传参。

### Lead 操作教训（本次实际踩到）

1. **不要给 Writer 写"怎么改"**。只转交审稿 MUST 原文 + 路径。本次三条 structural 由 Lead 简报直接制造。
2. **派发任何角色前先读它的 `instructions.md`**。字段名、判定口径都在那里；凭 Skill 记忆复述会烧轮次。
3. **先取回执，再 `complete-role`**。宿主真实会话 ID 只在回执里；不要先提交再找。
4. **技术终态与文学结论要分开**。子代理撞轮次上限属 `failed`，不能当完成提交；但已产生的正文要保住（本次靠"有限核验轮"续上，未重写正文）。
5. **改一处必须当场核对全局**，尤其是空间/数量/持有一类跨段不变量。人肉核对不可靠，物理账本（P0-2）才是解法。
6. **收敛靠删除，不靠补充**。加法轮的实测收敛率为零。

## 六、验收标准（迭代后怎么算成功）

在同一本书、同一题材、干净环境下重跑第一章：

- 角色调用 ≤ 10 次，墙钟 ≤ 3000s；
- 集中修订 ≤ 2 轮；任何锚点最多出现 2 次；
- 正文字数从初稿到 ready 变化在 ±10% 内；
- Writer capsule 中确实存在正面参照（可断言 P2 含「学 …」条目）；
- 无 `evidence/` 之外的会话归属错误；`--session-id` 全部可追溯到宿主回执；
- 人工判断：正面参照的变化能在正文里被观察到（同一前提写两稿，只改勾选的基因）。

最后一条是本系统不认证的部分：**文学价值仍由作者判断**，流程只保证不浪费作者的时间。
